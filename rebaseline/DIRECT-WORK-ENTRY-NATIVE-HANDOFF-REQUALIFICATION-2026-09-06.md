## 1. Decision and bounded rationale

Make direct Work entry explicit for recognizably substantial work. Keep Chat for bounded conversational work and NWT for actual transfers. Work can develop the problem, options and approach inside an authorized outcome; it does not require Chat to complete these first. This is an operating-allocation clarification compatible with existing canonical semantics, not a new work architecture.

The previous baseline did not forbid direct Work entry. Its product model nevertheless described substantial work chiefly through an already-formed conversational Work Object, and NWT assigned formation to Chat in its responsibility paragraph. That emphasis could encourage avoidable pre-work in Chat. It is a plausible contributing condition, not a proven cause of the audited episode.

Official current guidance supports direct entry and interactive Work. **A universally available, context-preserving “Continue in Work” or “Transfer to Work” control is not established by the sources inspected.** Native transfer is therefore a conditional preference, not an assumed operational dependency. Documented cloud-Work synchronization, Project context, and Codex host handoff must not be substituted as proof of Chat-conversation conversion.

### Qualified realization preference

1. **Direct Work entry:** for an already recognizably substantial contribution. Begin with intent and relevant boundaries; Work can recover context and develop the approach.
2. **Native transfer, where actually available and suitable:** when an existing Chat grows into such work. Use transferred context and add only missing material orientation. Neither a new Work toggle nor a shared Project alone certifies complete conversation transfer.
3. **AI-prepared context-complete handoff:** when native transfer is unavailable, unreliable or inappropriate. Reuse accessible Project/source context and supply only missing decisions, corrections, scope, quality and authority. Full manual serialization is unnecessary unless the exact transcript is material.

The order is an operating preference under availability and context conditions, not a claim that option 2 exists everywhere or an automatic routing mechanism. The fallback may still require the Human to open Work and submit the prepared request; it should not require the Human to reconstruct or author it.

## 3. Operating allocation

| Situation | Operating choice |
|---|---|
| **Start in Chat when…** | The useful result is conversation, a focused answer, lightweight exploration, calibration or bounded reasoning. Multiple functions can occur in one conversation. |
| **Start in Work when…** | Sustained research, material decision analysis, strategy/design, production or execution is foreseeable and Work materially improves the result. A qualified problem frame can be the deliverable; the solution need not be known. |
| **Move Chat → Work when…** | The next contribution has become substantial and benefits from Work. Transfer the existing qualified state before substantial further Chat execution, using the best actually available route. |
| **Stay in Work when…** | Research, questions, option formation, decision analysis, refinement or Human steering remain within the authorized work. A change of function alone is no reason to change surface. |
| **Return / re-enter when…** | A protected purpose, scope, quality, method, commitment or authority boundary needs the legitimate owner's contribution. Resolve it within Work where suitable; switch surfaces only for a material benefit. |

No arbitrary duration, word count, step count or universal intake checklist is introduced. Work may perform several or all of the existing nine functions. Those remain descriptive transformations; Skills remain differentiated methods. Native Work selects a fitting available method, including a narrower provider where necessary. Neither direct entry nor a Skill name establishes valid analysis.
