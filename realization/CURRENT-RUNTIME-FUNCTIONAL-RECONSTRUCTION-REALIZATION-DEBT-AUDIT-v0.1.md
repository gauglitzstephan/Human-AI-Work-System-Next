## 1. Why this audit exists

This is **not** a new architecture cycle and not a clean-sheet runtime design.

It executes the repository's original lineage/evaluation discipline:

- `ARCHITECTURE-METHOD.md`: recover/provisionally retain qualified prior design unless a named reopen trigger exists; do not re-derive accepted work by default; runtime realization follows architecture and must preserve semantics;
- `EVALUATION-STRATEGY.md`: compare against the best realistic incumbent, not a weak control; distinguish behavioral performance from conceptual coherence; ablate mechanisms only after a richer system shows value; do not optimize measurable proxies that fail to represent the intended outcome;
- `README.md`: runtime semantic compilation and Knowledge-Capital/capability placement are realization questions, not permission to replace a working runtime with a smaller invented one;
- `references/FRONTIER-USER-CHALLENGE-v0.1.md`: product surfaces such as Projects, Skills, Agents, Apps, Tasks and Codex are candidate realizations; they do not themselves define the Human–AI Work System.

### Audit rule

> **No incumbent function is removed, relocated or demoted because another carrier looks cleaner.**

A carrier change requires evidence of:

```text
material problem with current placement
+ credible alternative carrier actually available
+ reliable activation/context transfer
+ equal or better behavioral performance for the claimed scope
+ acceptable total-system complexity/economics
```

Character count is not a success metric.

# 3. Evidence classes used

- **E1 — Direct real-use evidence:** observed success/failure/correction in real work.
- **E2 — Qualified prior / accepted architecture evidence:** previously tested/accepted bounded mechanism.
- **E3 — Current platform/runtime evidence:** actual product precedence/capability/context constraint.
- **E4 — Plausible but unproven realization hypothesis:** architectural rationale without enough behavioral transfer evidence.

Disposition strength follows evidence, not elegance.

# 6. Realization debt audit

A `debt` below means a demonstrable or bounded realization problem. It does not automatically justify changing the CI.

## RD-01 — Cross-surface semantic inheritance / conformance

**Status:** REAL / E3.  
**Problem:** Global Custom Instructions are not guaranteed to remain active in every execution context. Project Instructions can override global CI; Work/Codex/Tasks/Apps have context/capability/permission differences.

**Affected incumbent function:** primarily F19, with F12–F15 potentially impacted downstream.

**What is justified:** additive context-transition/conformance tests and, if needed, minimal compatibility packaging for the affected surface.

**What is not justified:** removing the incumbent global semantics before the alternate surface proves equivalent coverage.

---

## RD-02 — Behavioral attribution / transfer evidence is insufficient

**Status:** REAL EVALUATION DEBT / E2 + evaluation strategy.  
**Problem:** The incumbent CI is a bundled historically evolved system. We do not have causal evidence showing which clauses can be disabled, relocated or replaced without regression.

**Consequence:** carrier moves are currently underidentified.

**Required resolution:** controlled ablation/transfer tests against the exact incumbent on representative work, using professional outcome quality, critical errors, state/authority integrity, Human correction burden, unnecessary work and recipient/use fitness—not token/character count.

---

## RD-03 — Reusable-capability / Knowledge-Capital promotion lifecycle remains open

**Status:** OPEN ROADMAP QUESTION, NOT CURRENT CI FAILURE.  
**Problem:** Some methods may eventually earn reusable Skill/workflow/Project-local capability status, but current evidence does not establish which ones, their invocation conditions, evaluator, versioning, transfer scope or retirement rules.

**What is justified:** test repeated successful methods for capability promotion where recurrence and value exist.

**What is not justified:** declaring B.6, foresight, assurance or other incumbent semantics to be Skills merely because a Skill carrier exists.

---

## RD-04 — Cross-context execution/readback mechanisms are under-specified in concrete product surfaces

**Status:** MATERIAL TEST GAP / E3.  
**Problem:** F19 specifies semantic preservation across handoffs, but exact Project/Work/Codex/App/Task realization is not yet behaviorally established.

**What is justified:** surface-specific fixtures where state, permissions, authority, completion and return can diverge.

**What is not justified:** a universal handoff document, room, agent, store or execution-contract object.

---

## RD-05 — CI active-context/salience competition

**Status:** HYPOTHESIS ONLY / E4.  
**Observation:** The incumbent CI is near the current 5k limit and contains many conditional methods.

**Not established:** that this causes material behavioral degradation, that shorter CI is better, or that local carriers would activate more reliably.

**Disposition:** **DO NOT TREAT AS DEBT UNTIL BEHAVIORAL EVIDENCE EXISTS.**

Character count has no independent optimization authority.

# 10. Evaluation path authorized by this audit

This is not a new framework. It is the existing `EVALUATION-STRATEGY.md` applied to the incumbent runtime.

For any proposed carrier change `X`:

```text
CONTROL
exact incumbent runtime with current CI

TREATMENT
incumbent runtime + one bounded additive/relocated mechanism X

TASKS
real or faithfully reconstructed heterogeneous work

MEASURES
professional outcome quality
critical errors / missed requirements
state + authority integrity
Human correction/review burden
unnecessary work / clarification / coordination
recipient/use fitness
runtime/transition success where relevant

PROMOTION
only if X creates material net benefit with no non-compensatory regression
```

If no material improvement is demonstrated, **KEEP INCUMBENT**.
