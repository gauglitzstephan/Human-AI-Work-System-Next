## 1. Observed failure

During real work on how to design an AI-native professional working system, the Human challenged the prior rule that contrasted open exploration with Formation.

The response and active Skill semantics allowed this inference:

```text
exploration is explicitly requested product
→ DIRECT may be appropriate
```

That relation is insufficient. Exploration can itself be materially open in purpose, question, search space, strategy, required professional/reference basis, evidence, output, or stopping/transition rule. In that state, directly generating exploratory content can prematurely collapse the work just as directly generating a solution can.

## 2. Exact localization

The static architecture already provides:

```text
Orchestrator selects minimum legitimate frontier
+ Formation when work is materially open
+ possible frontier outputs include exploration/research/decision/execution
```

The v0.2 Skill compressed this into:

```text
NEW/CHANGED
→ DIRECT or FORMATION
+ exploration may be DIRECT when exploration is the requested product
```

This loses the type distinction:

```text
readiness of next frontier
≠ Work Function
≠ requested product label
```

The defect therefore localizes first to Runtime semantic compilation and validation coverage, not to a missing static owner.

## 3. Assurance correction

The prior Work matrix contained a clean mailbox-history ideation control. It established only that one bounded low-stakes ideation request could remain direct without ceremony.

It did not establish that:

- all explicit exploration is ready;
- exploration strategy is already formed;
- no upstream professional/reference or context acquisition can change the exploration;
- the Skill is generally reliable as an automatic Entry controller.

The broader v0.2 claim is therefore withdrawn pending repair and representative forward testing.

## 4. Repair relation

Replace activity-based `DIRECT vs FORMATION` selection with a readiness decision about the next legitimate frontier:

```text
bind Parent/state/trigger
→ identify next legitimate transition
→ identify candidate Work Function
→ test whether that frontier is sufficiently formed
   ├─ READY: perform the selected Work Function
   └─ NOT READY: form only what can change that frontier
→ execute/integrate when ready
→ re-enter selectively on material change
```

Exploration, research, decision, design, execution, assurance, and observation can each be the selected Work Function after the readiness test.

## 6. Failure-detection criteria for live forward test

A live case fails when any of the following occurs:

1. exploration content begins before a materially open exploration strategy is formed;
2. a bounded ideation/translation case receives disproportionate Formation;
3. the Human is asked to perform AI-resolvable context orchestration or source discovery;
4. a professional route is qualified before its performance/reference basis exists;
5. an existing Parent/frontier is replaced by the newest message or artifact;
6. a plan is returned where the ready frontier requires execution and an actual Work Product;
7. the model claims general reliability from marker presence or self-review.

Required live cases before any v0.3 replacement or promotion:

```text
open exploration whose strategy is materially open
+ bounded low-stakes ideation negative control
+ missing professional-method case
+ incomplete-context acquisition case
+ established-Parent continuation
+ selected-route to execution transition
```

Run at least one clean automatic-activation case and one explicit-invocation diagnostic case. Record exact prompts, observed markers, substantive behavior, Human corrections, and claim boundaries.
