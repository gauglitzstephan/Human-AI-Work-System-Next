# End-to-End Real-Use Validation Protocol v0.1

**Status:** CANDIDATE VALIDATION PROTOCOL — next program after static architectural closure.  
**Date:** 2026-08-20  
**Architecture under test:** `architecture/E2E-WORK-ARCHITECTURE-CANDIDATE-v0.1.md`  
**Runtime contract under test:** `realization/E2E-OPERATING-RUNTIME-CONTRACT-CANDIDATE-v0.1.md`  
**Static review:** `reviews/E2E-STATIC-CLOSURE-REVIEW-v0.1.md`

## 1. Purpose

Test whether the static-complete candidate can actually carry heterogeneous professional work End-to-End without hidden Human bridging, state/control loss, professional-quality collapse, or process ceremony.

This validation must **not** rely on chat memory as the evidence store.

Each material case persists its evidence/state in the repository (or another explicitly designated authoritative validation store) at defined evidence boundaries.

## 2. Claims under test

The protocol may support only claims that the evidence actually establishes.

Primary behavioral hypotheses:

1. incomplete real input can be transformed into a decision-ready work basis without premature means/route collapse;
2. the Orchestrator selects the minimum legitimate next frontier while preserving parent state and qualified work;
3. Professional/Reference Intelligence actually activates when material rather than remaining policy prose;
4. Commitment and Promotion/State Transition remain distinct in behavior;
5. material Gates actually withhold blocked downstream work;
6. execution produces and integrates the actual requested Work Product rather than process/meta substitutes;
7. next-use refinement catches AI-resolvable recipient/craft defects before Human acceptance;
8. claim-matched assurance does not promote narrow QA into broader readiness;
9. transition/use/outcome boundaries remain distinct;
10. learning produces bounded change candidates rather than automatic global mutation;
11. simple/bounded work does not acquire unnecessary ceremony.

## 3. Validation design principles

### Real work first

Use actual current work with genuine value and consequences. Do not create synthetic test queues merely because the architecture contains functions that could be tested.

A synthetic/isolation test is justified only when:

- an observed failure cannot be localized with ordinary real-use evidence; and
- the controlled test has positive incremental information value for a concrete decision.

### Whole-task evidence

Evaluate the complete path, not only isolated semantic hooks.

```text
raw input / trigger
→ formation / decision
→ selected basis
→ work formation
→ execution / integration
→ refinement / assurance
→ transition / use where applicable
→ evaluation / learning / closure
```

### No self-confirming PASS

Architecture/Runtime authorship and producer self-review are not sufficient assurance for strong End-to-End claims.

Use independent evidence sources, deterministic checks, different professional/reference lenses, recipient/use evidence, or Human judgment only when they have actual detection capability.

### Evidence boundary

Record only state-changing/material evidence. Do not create a ledger entry after every conversational turn.

## 4. Minimum representative work classes

The initial validation wave should contain **at least four actual work cases** whose mechanisms differ materially.

### E2E-01 — Open consequential decision

Characteristics:

- initial frame/goal is materially open;
- multiple solution mechanisms are plausible;
- evidence/future uncertainty can change the route;
- commitment can be staged/reversible;
- primary output is a decision/recommendation rather than an artifact.

Must exercise:

```text
Frame / Purpose / Outcome
+ peer alternative integrity
+ Reference / Evidence
+ Future / uncertainty treatment
+ Outcome Mechanism
+ feasibility / trade-offs
+ decision / commitment design
+ Closure / no unnecessary research
```

Historical risks covered: first-salient-route optimization, non-peer option mixing, false precision, research theater, decision-without-recommendation.

### E2E-02 — Existing-system repair / change

Characteristics:

- real pre-existing artifacts/state/requirements/workflow exist;
- authoritative state must be retrieved;
- some existing components should be preserved;
- changes may affect controlling/persistent state.

Must exercise:

```text
current-system recovery before redesign
+ authoritative-state / derived-view distinction
+ preserve / repair / retire / replace
+ Promotion / State-Transition Control
+ legitimate write path + readback
+ Parent-Work Continuity
+ bounded reopen
```

Historical risks covered: redesigning imagined system, stale authority pointer, parallel truth layer, child/local work becoming root, self-authored state loops.

### E2E-03 — High-stakes professional recipient-facing Work Product

Characteristics:

- professional/domain method matters;
- artifact/craft quality matters;
- Human voice/judgment/acceptance may be legitimately material;
- deterministic and recipient-level assurance are both possible;
- downstream use/rehearsal/recipient context differs from artifact production.

Must exercise:

```text
Professional + Reference Intelligence activation
+ substantive source Work Product maturity before final artifact production
+ artifact/craft method
+ Human Gate only where legitimate
+ actual wait/enforcement if Gate is material
+ Execute + Integrate
+ Next-use Refinement
+ deterministic verification
+ intended-use / recipient validation
+ transition/use readiness
```

Historical risks covered: Bergfreunde professional-method failure, artifact QA failure, blocker-only Human gate, S-Payment first-impression/voice failure, process/meta substitution, Human as first QA detector.

### E2E-04 — Persistent multi-turn / multi-surface work program

Characteristics:

- work spans multiple turns and/or surfaces/tools;
- parent program has child Work Units;
- state can diverge;
- handoffs/continuation occur;
- at least one material promotion/change may occur.

Must exercise:

```text
Parent-Work Continuity
+ distributed typed state
+ authoritative state-domain ownership
+ handoff preservation
+ capability/access/authority revalidation across surfaces
+ Promotion/readback
+ no implicit child-root switch
+ selective reopen / continuation / closure
```

Historical risks covered: `Next` continuing local salience instead of parent program, false cross-surface inheritance, persistent-state divergence, room/project reification.

## 5. Optional fifth class — delayed external outcome

Add only when real work naturally supplies it.

Characteristics:

- Work Product can be produced/transitioned now;
- intended outcome occurs later or outside AI visibility;
- outcome observer/evidence source/horizon are identifiable.

Must exercise:

```text
transition ≠ use ≠ outcome
+ outcome observation design
+ attribution limits
+ signposts / adaptation
+ delayed closure / monitor / handoff
```

## 7. Case scoring

Score each case on these dimensions:

| Dimension | Core question |
|---|---|
| End-to-End completeness | Did any material transformation have to be improvised outside the model? |
| Outcome / Work Product fidelity | Was the actual required Work Product/outcome pursued rather than a proxy/meta artifact? |
| Professional quality | Was the applicable method/craft bar actually resolved/applied? |
| State integrity | Were authoritative/working/accepted states kept distinct and current? |
| Decision / promotion integrity | Were recommendation, decision, commitment, acceptance, authorization, and promotion kept type-correct? |
| Human agency / burden | Was Human contribution used where valuable/authoritative without becoming default AI QA? |
| Orchestration | Did the Runtime select the right next frontier rather than local salience/meta-work? |
| Enforcement | Did material Gates/transition conditions actually stop blocked downstream work? |
| Assurance | Did assurance match the exact claim and detect material failure modes? |
| Realization | Were transition/use/outcome boundaries handled where relevant? |
| Proportionality | Was process/tooling/research/state ceremony justified by value? |
| Learning / repair | Were failures localized and unaffected qualified state preserved? |

Use:

```text
PASS
PARTIAL
FAIL
UNVERIFIED / NOT ACTIVATED
```

`NOT ACTIVATED` is not a defect when a conditional function was genuinely immaterial.

## 8. Critical failure conditions

A single case is a **critical architecture/runtime failure candidate** when one or more occur:

1. an End-to-End material transformation is required but has no architecture owner/mechanism;
2. a required critical function exists only as prose and cannot be effectively realized/enforced in the intended runtime;
3. a candidate/local child state becomes controlling without legitimate promotion/authority;
4. a strong readiness/outcome claim is made without assurance capable of establishing it;
5. the Human must repeatedly invent or bridge a material AI-resolvable function not represented/activated by the system;
6. runtime implementation necessarily loses a material architecture semantic with no owner;
7. two architecture semantics create an unresolved ownership/authority contradiction.

These trigger static-architecture reopen consideration.

By contrast, local model variance, domain/craft defects, tool failures, missing method packs, or one missed deterministic check should be repaired at the responsible local/runtime/method layer when the architecture already represents the mechanism.

## 9. Human burden measure

For each case record whether the Human had to:

- supply exclusive context/truth;
- express values/preferences;
- contribute expertise;
- exercise authorship/voice;
- accept/decide/authorize;
- detect AI-resolvable factual/logic/craft/constraint defects;
- reconstruct lost state;
- redirect meta-work back to the actual outcome.

The first five may be legitimate contributions. The last three are negative signals unless the case requires otherwise.

## 10. Runtime enforcement observation

For every material Gate/promotion/transition capture:

```text
policy existed?
transition decision made?
effective control/enforcement existed?
downstream action actually withheld/permitted correctly?
actual authority level/path established?
```

This is required because historical evidence shows:

```text
policy semantics present
≠ effective transition enforcement
```

## 11. Acceptance logic after the wave

Do not aggregate by simple average.

### Architecture completeness survives

If:

- no case exposes an unowned material transformation;
- required architecture mechanisms remain realizable without semantic distortion;
- observed defects localize to runtime/method/tool/artifact execution rather than missing architecture semantics;
- no critical state/authority contradiction appears.

Then retain:

> static architectural completeness candidate survives representative use.

### Runtime/operating acceptance

Requires positive evidence that the operating Runtime contract actually activates across the representative cases with acceptable Human burden, professional quality, state integrity, proportionality, enforcement, and closure.

Acceptance must remain scoped to tested runtime/product/surface conditions.

### Static architecture reopen

Only for a named material trigger from §8 or a legitimate changed requirement/scope.

## 12. Program discipline

During this validation program:

```text
real problem
→ operate candidate
→ persist material evidence
→ localize defect
→ repair lowest responsible layer
→ re-run only affected / representative work as justified
```

Do **not** launch another architecture package merely because a local case fails.

Do **not** declare success from static regression, one successful chat, or a favorable self-review.

Do **not** leave material evidence solely in transient conversation history.
