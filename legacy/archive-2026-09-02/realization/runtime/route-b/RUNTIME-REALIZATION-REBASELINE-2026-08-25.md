## Demotion

The merged runtime implementation under `realization/runtime/route-b/v0.5-chatgpt-runtime/` is retained as historical Candidate evidence but is not an approved installation payload.

The static semantic-fidelity findings remain evidence about that specific compilation. They do not establish that the compilation strategy is the best or correct ChatGPT realization.

## Rebaseline question

Determine how the accepted semantics should be distributed across current ChatGPT mechanisms so the system is professionally strong, native, sparse in permanent context and progressively disclosed where appropriate.

Evaluate three realization classes:

### A. Full Kernel in permanent Instructions

Global and Project Instructions carry nearly all canonical invariants.

Evaluate for:
- semantic coverage;
- context burden;
- duplication of native behavior;
- instruction interpretability;
- maintenance/control-ratchet risk;
- Project override implications.

### B. Thin behavioral Instructions + progressive-disclosure Skills/Methods

Permanent Instructions carry only stable global behavior/outcome/authority/quality constraints. Formation and professional methods are loaded through focused Skills/Method Packs when relevant.

Evaluate for:
- trigger reliability;
- semantic loss risk;
- professional-method availability;
- context efficiency;
- native-runtime leverage;
- cross-surface behavior.

### C. Hybrid

Permanent Instructions carry only universal invariants whose omission would materially degrade ordinary work; the rest is progressively disclosed through focused Skills/Methods or recovered from authoritative project state.

Evaluate against the same requirements.

## Required functional allocation

The selected realization must make explicit ownership for:

- global working behavior and quality orientation;
- Project-local authority/context;
- Formation and sufficiency;
- Work Function identification;
- professional Method discovery and execution;
- Research/Evidence capability;
- System-Development professional methods;
- native planning/tools/delegation/integration;
- Human contribution/authority;
- assurance;
- state continuity and repository writes;
- transition/use/outcome boundaries.

Do not equate a Work Function with a Skill. Create a Skill where reusable professional method, trigger logic, resources or specialized execution justify progressive disclosure.

## Current method assets

`methods/METHOD-REGISTRY-v0.1.md` currently indexes six System-Development Candidate Method Packs:

1. System Architecture / Requirements;
2. Existing-System Recovery;
3. RCA / Failure Localization;
4. Runtime Compilation / Semantic Regression;

These packs are candidate reusable method assets, not proof that one monolithic `system-development` Skill is the optimal packaging. Packaging must be chosen based on trigger coherence, shared resources, context economy and execution quality.

A reusable Research/Evidence capability remains a distinct candidate because evidence strategy, source qualification, synthesis, uncertainty and context engineering recur across domains; its exact packaging remains to be formed and assured.

## Decision criterion

Select the realization with the lowest permanent-context, coordination and maintenance burden among those that satisfy non-compensatory floors for:

- professional quality;
- reality/epistemic integrity;
- authority/effect integrity;
- continuity where material;
- claim-matched assurance;
- Human agency/autonomy;
- intended-use fitness.

No arbitrary character target is a requirement. Carrier limits are feasibility constraints only.
