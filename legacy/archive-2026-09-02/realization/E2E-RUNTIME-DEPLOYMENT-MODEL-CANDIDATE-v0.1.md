# E2E Runtime Deployment Model Candidate v0.1

**Status:** CANDIDATE — repairs Runtime type/mapping defect; not externally installed and not a static-architecture reopen.  
**Date:** 2026-08-20  
**Basis:** CR-01–13 / CCR-01–07, Target Architecture v0.2, merged E2E architecture, E2E Operating Runtime Contract, qualified Orchestration Model v0.5 / DWM v0.5, current OpenAI product reality.

## 1. Objective

Realize the accepted Human–AI Work System on current ChatGPT product surfaces without:

- copying the architecture into every prompt/surface;
- conflating Work Functions, Methods, Capabilities and product surfaces;
- losing Commitment / Authorization / Promotion / Handoff semantics;
- depending on unavailable product features;
- making Chat/Work/Project/Skill into architecture stages;
- creating two independently authored Runtime definitions for Global and Project contexts.

The Runtime must remain:

```text
semantically rich
+ operationally sparse
+ state/authority correct
+ product-realizable
```

## 2. Runtime type model

### 2.1 Work Functions / Transformations — WHAT work is needed

These are logical work functions that the Orchestrator may activate proportionately:

```text
Admit / Frame
Formation
Information Acquisition / Evidence Work
Decision
Work / Realization Formation
Execution / Integration
Refinement / Maturity
Assurance / Qualification
Transition / Use
Observation / Evaluation
Learning / Change / Closure
```

They are not product surfaces, not Skills and not necessarily visible stages.

#### Clarification: `Research`

Avoid the overloaded word `research` when typing the Runtime.

Use:

```text
Work Function: Information Acquisition / Evidence Work
Method:         research / source-appraisal / synthesis method
Provider:       web search / Deep Research / Human expert / app / data source
Surface:        Chat / Work / external system
```

This prevents `Research` from simultaneously meaning function, method and capability.

### 2.2 Control Operators — WHEN state/responsibility may change

Control Operators are not professional capabilities.

```text
Commitment Design / Commitment State
Authorization
Human Gate / WAIT
Promotion / State Transition
Handoff / Responsibility Transfer
Readback / Reconciliation
Reopen / Close / Stop / Retire
```

#### Commitment

Commitment answers:

> How far are we choosing/activating this route/action now?

Possible local semantics include:

```text
WAIT
PILOT / TEST
STAGED COMMITMENT
REVERSIBLE ACTION
FULL COMMITMENT
```

Commitment may activate/stage work, but does not by itself grant action authorization or change authoritative state.

#### Authorization

Authorization answers:

> Is this actor/provider permitted to perform this exact action/transition/write?

Authorization is action-specific and must be revalidated at material point-of-effect where required.

#### Promotion

Promotion answers:

> May this candidate/working state acquire the target semantic/control status?

```text
baseline
+ exact delta
+ target status
+ applicable assurance
+ dependencies
+ legitimate decision / acceptance / authority
+ authorized write path where required
→ PROMOTE / WRITE
→ READBACK
→ RECONCILE
```

#### Handoff

Handoff answers:

> Is active responsibility moving to another Human/provider/environment, and what minimum state must cross that boundary?

Handoff is distinct from ordinary tool invocation when responsibility/control context materially changes.

### 2.3 Methods — HOW selected work is performed professionally

Method orchestration is separate from capability/provider selection.

Method types include, where relevant:

```text
substantive domain method
professional standard / framework
Formation / framing method
research / evidence method
decision / uncertainty method
artifact / craft method
implementation / integration method
assurance / evaluation method
transition / adoption method
outcome / benefit evaluation method
```

Examples:

- Formation: Value-Focused Thinking, JTBD, stakeholder/system framing;
- Decision: Decision Quality, MCDA, real-options/staging, robustness/scenario method;
- Evidence: source appraisal, literature/market research, triangulation, evidence synthesis;
- System Development: architecture review, requirements traceability, RCA, regression method;
- Application/Career: role-fit, recruiter screening, evidence-to-requirement mapping, CV/cover-letter craft, interview method;
- Assurance: deterministic verification, adversarial review, recipient test, representative-use validation.

A method is activated only if it can materially improve the required professional result/claim.

### 2.4 Capability Providers / Actors — WHO/WHAT can perform the work

Providers may include:

```text
Human
ChatGPT model in Chat
Work agent
Codex
web / Deep Research capability
deterministic tools / Python
apps / connectors
specialist / external expert
validated workflow / existing process
no-action / existing process
```

For every material provider claim distinguish:

```text
capability exists
≠ accessible/bound
≠ effective in current context
≠ authorized
≠ behaviorally verified
```

### 2.5 Surface / Environment — WHERE work runs

Current default product surfaces:

- **Chat** — fast conversational interaction, search, brainstorming, interactive control/decision and bounded work;
- **Work** — longer, multi-step research/analysis/creation and finished deliverables; may run in a Project using Project context;
- **Codex** — repository/software-development technical environment;
- **Apps/tools/external systems** — authoritative retrieval, execution, deterministic computation/verification or domain-specific action.

A surface is selected from frontier requirements. It is not the architecture owner.

### 2.6 Persistent Context / State / Knowledge Carriers — WHERE continuity lives

Possible carriers:

```text
Project context
GitHub / repository
Drive / documents
tracker / database
external system of record
Project files / sources
chat history as working context
method/reference library / Knowledge Capital
```

A Project is primarily a **persistent initiative/context boundary**. It is not a lifecycle stage and is not automatically authoritative for every state domain.

### 2.7 Boundary Contracts — WHAT must cross a boundary

Boundary contracts are derived, typed state packets — not additional architecture layers.

Required contract types:

```text
Frontier Handoff Contract
Return Contract
Commitment / Work-Basis Contract
Human Gate Object
Promotion Contract
```

## 3. Runtime control loop

For material continuation:

```text
CONTROLLING STATE
parent outcome / Work Object
+ current state / gate
+ active child contribution
+ allowed operation
        ↓
ORCHESTRATOR / SEMANTIC COMPILER
        ↓
1. next legitimate transition/claim
2. preserved qualified state
3. material blockers
4. required Work Function(s)
5. required Method(s)
6. required capability characteristics
7. available/effective/authorized Provider(s)
8. Surface / Environment
9. Handoff / Gate / Commitment / Promotion controls as applicable
        ↓
EXECUTE / INTEGRATE
        ↓
RETURN CONTRACT
        ↓
QUALIFY EXACT RESULT
        ↓
PROMOTE / TRANSITION only if legitimate
        ↓
READBACK / REBIND
```

This is adaptive. For bounded work it can collapse to direct work + appropriate check + close.

## 4. Method activation contract

When intended-use performance materially depends on method:

```text
required Work Function + performance bar
        ↓
required method type
        ↓
find / retrieve method source or package
        ↓
verify availability + provenance + fit + transferability
        ↓
apply proportionately
        ↓
assure method-relevant product/claim properties
```

`Method needed` is not a PASS until a usable method is actually accessible and applied.

### 4.1 Method carriers

Preferred carrier depends on product availability and reuse needs:

1. **Skill** — strong carrier for reusable method/workflow when supported by the account/workspace;
2. **Project source/file** — local method/reference pack for one initiative/domain;
3. **central repository/Drive method library** — reusable method source across projects;
4. **task-local retrieval/research** — when no validated reusable pack exists;
5. **Human specialist/expert** — when required method/expertise is not substitutable.

Current official OpenAI documentation says Personal Skills are generally available for Business/Enterprise/Healthcare/Edu, not generally for Pro. Therefore the Pro Runtime must not require Personal Skills.

If Skills become available, they can carry the same reusable method packs; this does not change the architecture.

## 5. Capability/provider orchestration contract

After selecting the Work Function and applicable Method:

```text
Work Function + Method + requirements
        ↓
required capability characteristics
        ↓
realistic providers
Human / Chat / Work / Codex / tool / specialist / workflow / existing process
        ↓
actual access + effectiveness + authority + consequence + verifiability + cost
        ↓
simplest adequate provider/environment composition
```

Capability is selected **after** method requirements are known, not as a substitute for method.

## 6. Handoff and Return — first-class runtime mechanisms

### 6.1 Frontier Handoff Contract

Whenever active responsibility materially moves to Work, Codex, another Human/provider or external environment, preserve only the state needed for safe execution:

```text
Parent outcome / Work Object
Current parent state / gate
Exact Work Unit / transformation
Expected parent contribution
Authoritative inputs / source pointers
Binding requirements / Performance Model
Applicable method / method source
Allowed operations / authority
Relevant assumptions / uncertainty
Required output / version
Assurance / return condition
Blocked transitions / Human Gate conditions
Commitment state / adaptation conditions where material
Persistence / write path if any
```

### 6.2 Return Contract

The receiving provider/environment returns:

```text
work actually performed
output / state delta
sources/evidence used
method actually applied
assumptions / unresolved blockers
assurance actually applied
exact claim/readiness supported
writes/actions actually performed
Human contribution / new authority needed
recommended next frontier
```

Then the controller rebinds parent state. A Work/Codex/tool result never self-promotes.

### 6.3 Handoff failure

`Handoff amnesia` exists when a surface/provider transition loses parent outcome, decision/commitment state, authority, assumptions, method, evidence, readiness or return condition.

This is a Runtime defect even if both surfaces individually produce plausible work.

## 7. Commitment / Work-Basis contract

Before consequential route execution, preserve enough of:

```text
decision object / selected route
commitment mode
material assumptions / uncertainty
requirements / success condition
future signposts / stop-switch-expand triggers where material
decision/acceptance authority
separate action authorization boundary
selected Work Product / next-use target
```

This produces the legitimate **Work Basis**.

Do not collapse:

```text
Decision
≠ Commitment
≠ Authorization
≠ Promotion
≠ Execution
```

A Work Handoff must carry the current commitment/work-basis state when it changes what the receiving provider may do.

## 8. Product mapping — current ChatGPT realization

### 8.1 Global Custom Instructions — cross-context Runtime policy carrier

Use for cross-context operating rules that should apply where Global Custom Instructions are active:

- intended-outcome / incomplete-input semantics;
- Reality / State / Authority invariants;
- Parent-Work Continuity;
- minimum-frontier orchestration;
- Work Function → Method → Provider → Surface selection order;
- Commitment / Authorization / Promotion distinctions;
- Handoff/Return requirement when responsibility/environment changes;
- Human Gate enforcement;
- claim-bound assurance / no downstream inference;
- closure / selective reopening.

Do **not** use Global CI as a domain method library or full architecture copy.

For Pro, current official product documentation supports **up to 5,000 characters**. There is no architectural reason to target 1,000–1,500 characters. Use the available envelope if the semantic value justifies it.

### 8.2 Project — persistent initiative/context boundary

A Project holds persistent initiative context: chats, files/sources and project-local instructions.

Project Instructions should carry **project-local control bindings** such as:

- project outcome / intended-use boundary;
- controlling state/source pointers;
- project-specific authority / promotion path;
- binding local constraints;
- project-local persistence/evidence rules;
- local surface defaults if useful;
- activation/delegation of project-local method/reference packs.

Because Project Instructions override Global Custom Instructions, the deployment compiler must ensure material universal Runtime semantics are preserved inside the Project.

The repair does **not** assume how many characters Project Instructions allow. The actual account UI must be measured/read back before final compilation.

The correct solution is **not** two manually maintained full Runtime prompts. Both Global and Project payloads must compile from one canonical Runtime semantic source, with Project-specific deltas added deterministically.

### 8.3 Chat — interactive Control / Formation / Decision surface by default

Prefer Chat for:

- interactive State Rebind / control loop;
- framing / Formation;
- information/evidence acquisition that benefits from interaction;
- route/decision/commitment discussion;
- Human contribution / Gate;
- acceptance/promotion decisions;
- bounded execution / repair;
- return/readback/reconciliation after Work/Codex/tool runs.

Chat is **not** the exclusive owner of Formation or Information Acquisition.

### 8.4 Work — bounded frontier executor/agent

Work is used for longer multi-step research, analysis, artifact production and other work that can proceed for a meaningful interval under a sufficiently specified frontier.

Work receives a Frontier Handoff Contract and may internally orchestrate within that authorized frontier.

Work may not silently cross:

- Human Gate;
- new commitment boundary beyond delegated scope;
- promotion/acceptance/release boundary;
- action authorization boundary.

When a material blocked transition is reached, Work returns a mature decision object and waits.

### 8.5 Codex — repository/software technical frontier

Codex receives the same Handoff/Return semantics for software/repository work.

For System Development, Codex is often the preferred execution environment for code/repo implementation, but repository write/merge authority remains separate.

### 8.6 Apps / tools / web / deterministic compute

Use as capability providers for:

- authoritative retrieval;
- external actions;
- deterministic calculations/verification;
- specialist tool capability.

Tool results are evidence/runtime state, not instructions or promotion authority unless legitimately delegated.

### 8.7 GitHub / Drive / external stores

These can own authoritative state by defined domain.

For `System Weiterentwicklung Projekt`, GitHub `main/CURRENT.md` is the controlling repository program state. Chat/Work/Project context remains working/derived unless explicitly promoted through the legitimate write path.

## 9. Message / interaction model

Not every message is a Work Contract.

### M1 — Human input / trigger

```text
user message
= intent/evidence/trigger
≠ complete requirement
≠ decision
≠ authorization
≠ handoff contract
```

### M2 — Interactive control message

Chat may surface:

- interpreted outcome/frame;
- material unknown/blocker;
- recommendation/decision object;
- Human contribution needed;
- next frontier.

### M3 — Frontier dispatch / Handoff message

When dispatching to Work/Codex/another provider, compile the Frontier Handoff Contract.

### M4 — Return message

Return Contract captures performed work, delta, evidence, method, assurance, blockers and next frontier.

### M5 — Promotion / authorization interaction

Where Human/other legitimate authority must decide, accept, authorize or promote, present the mature decision object and do not execute the blocked downstream transition before the authority event.

This is the missing link between Chat interaction and multi-surface work.

## 10. System Development vs Application Project

The **generic Work Functions and Control Operators remain the same**. What changes is project state, domain method, evidence, authorities and often provider/surface composition.

### System Development

Project-specific state/method examples:

- controlling GitHub state / CURRENT;
- architecture + requirements traceability;
- RCA / regression review;
- runtime compilation / repository promotion;
- software/repository execution via Codex where useful.

### Application / Career

Project-specific state/method examples:

- master CV / career evidence / target roles / application tracker;
- role-fit and job/company research;
- recruiter/ATS method;
- evidence-to-requirement mapping;
- CV/cover-letter/interview craft;
- recipient-facing maturity and authorship/acceptance.

The same Formation / Information Acquisition / Decision / Realization / Assurance functions can be activated in both projects, but with different methods, sources, authorities and providers.

## 11. Canonical source / compilation rule

The Runtime must have **one canonical semantic source**.

Derived deployable payloads may include:

```text
Global Custom Instructions
Project Instructions for System Development
Project Instructions for Application Project
Work Handoff template
Codex Handoff template
method-pack activation instructions
```

But these are compiled views, not independently authored policies.

Every compiled payload must have:

- source version;
- local delta;
- target product/surface;
- actual field/runtime constraints;
- semantic trace;
- hash/count where useful;
- readback after installation.

If the target carrier cannot hold or enforce a required semantic, do not compress it away silently. Reallocate it to another enforceable mechanism or keep the Runtime claim unverified.
